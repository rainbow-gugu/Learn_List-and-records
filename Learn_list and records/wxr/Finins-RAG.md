SSE :
**SSE（Server-Sent Events，服务器推送事件）** 是一种基于 HTTP 协议的**单向长连接**实时通信技术。

- **工作方式**：客户端发起一次 HTTP 请求，建立连接后不断开，服务器可以持续、分批地向客户端推送数据，直到连接关闭。

- **核心特点**：
  - 单向通信：只能服务器 → 客户端推送，客户端无法通过这条连接发数据
  - 基于标准 HTTP：复用 HTTP 协议，无需额外端口，兼容代理、防火墙
  - 内置自动重连：连接断开后浏览器会自动重试
  - 数据格式轻量：`text/event-stream` 格式，按行传输事件
- **典型场景**：实时消息通知、数据大屏、日志实时流、股票行情推送等 “服务器主动发、客户端只接收” 的场景。

> 
> 和 WebSocket 的区别：WebSocket 是**双向**长连接，适合聊天、游戏等需要客户端也发数据的场景；SSE 更轻量、更简单，纯推送场景优先用 SSE。
I/O密集型:
**I/O 密集型（I/O-bound）** 是对程序负载特征的分类，和「CPU 密集型」相对：
| CPU 密集型 | 大量运算、逻辑计算 | 视频渲染、加密解密、算法计算 |
| --- | --- | --- |
| I/O 密集型 | 等待输入 / 输出完成，CPU 大部分时间空闲 | 网络请求、文件读写、数据库查询、**长连接保持** |
## 3. async 异步为什么能 “不阻塞、高并发”

要理解 async 的价值，先看**同步阻塞模型**的问题：

### 同步阻塞（传统多线程模式）

每来一个客户端连接，就开一个线程专门处理它。

- 当连接处于 I/O 等待时（比如 SSE 等数据、等数据库返回），这个线程会被**挂起阻塞**，啥也干不了，只能傻等
- 如果有 1 万个 SSE 长连接，就要开 1 万个线程
- 线程本身有内存开销（每个线程约占几 MB），线程切换也有 CPU 开销
- 结果：连接数一多，系统资源先被线程耗尽，CPU 反而很闲

### async 异步非阻塞模型

`async` + 事件循环 + I/O 多路复用（底层是操作系统的 epoll/kqueue），彻底改变了调度方式：

1. 程序跑在一个（或少量几个）线程里，由**事件循环**统一调度所有任务
2. 遇到 I/O 操作（比如等待数据、sleep、读网络）时，用 `await` 标记暂停点，**线程不会阻塞等待**，而是立刻去处理其他任务
3. 当 I/O 操作完成时，事件循环会收到通知，再回到之前的暂停点继续执行后续代码

### 核心优势

- **不阻塞**：I/O 等待时线程不闲置，始终在处理有效任务
- **高并发**：少量线程就能承载成千上万的长连接，因为空闲连接不占用线程
- **低开销**：省去了大量线程的内存和切换成本

> 
> 注意：async 不是让单个请求变快，而是让系统**整体吞吐量大幅提升**—— 同样的硬件，能同时处理的连接数是同步模型的几十到上百倍。
4.为什么SSE一定要配async
1. SSE 是长连接，每个客户端要占一条连接
2. 连接大部分时间在等待数据，属于**典型 I/O 密集**
3. 如果用同步模型，1 条连接占 1 个线程，连接多了系统直接扛不住
4. 用 async 异步模型，连接等待时不占线程，少量线程就能维护海量 SSE 连接

这就是 “async 让它在等待时不阻塞、能并发处理多个请求” 的完整含义。
