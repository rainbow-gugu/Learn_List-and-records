RAG分块
父子分块策略:
父->保存完整上下文，存在DB里，子->从父块里面切出来的小块，子块生成embedding,存入向量数据库


检索过程:
用户query->embeeding->取向量数据库查找
命中子块->通过子块外键,查询数据库，取出父块，父块送入LLM做答案生成，




RAG天生的矛盾，块越小，embedding语义越聚焦，但上下文不完整，容易断章取义，块越大，上下文虽然完整，但embddding容易泛化，局部细节匹配差，检索命中率下降


父子分块在这里能够两者兼备

[O父子分块把「检索任务」和「LLM 生成任务」拆开，交给两种不同尺寸的块，各司其职：

1. **子块（小块）：专门负责【检索】**
从父文档切割出细粒度子块（100~300token），对子块向量化存入向量库。
   - 优势：片段短、语义聚焦。用户提问的局部知识点，很容易和子块向量匹配，**提升检索精度**。
   - 子块**不会直接丢给大模型回答问题**，只用来做匹配，找到对应的父块 ID。
2. **父块（大块）：专门负责【给 LLM 生成答案】**
父块是包含该子块的完整上下文段落（800~2000token），父块**不入库向量库**，只存在关系数据库，和子块做外键绑定。
   - 当向量检索命中某个子块，拿到子块对应的父块 ID，去数据库取出**完整父块**。
   - 把完整父块送入 LLM 做推理，保证上下文完整，不会因为片段缺失造成回答片面、断章取义。

## 一句话概括原理

> 
> 检索用小块（子块）保证找得准；生成用大块（父块）保证信息全。**检索和生成使用两套不同粒度的文本，从而绕开单一块大小的两难取舍。**



### ✅ 优点

1. **检索精度 + 上下文完整性兼得**：用小块做精准检索，大块提供完整上下文。
2. 降低向量混淆：子块聚焦局部信息，embedding 更容易匹配用户问题。
3. 保留全局信息：不会因为只取一小段子块，造成断章取义。

### ❌ 缺点

1. 存储成本上升：需要两份数据，向量库存子块，关系库存父块。
2. 检索多一次 DB 查询，增加链路延迟。
3. 父子块绑定关系要维护，文档更新时父子都要同步更新。

# Agent Loop（Agent 循环，面试核心，ReAct 就是这个 loop）

> 
> 一句话：**普通 LLM 是一次输入→一次输出；Agent Loop 是一个 while 循环，不断：思考→调用工具→拿到结果→把结果塞回上下文，反复迭代，直到任务完成**。
> 标准名称：**ReAct Loop（Reason-Act-Observe，思考 - 行动 - 观察）**

## ✅ 一轮 Loop 完整 4 步（每一轮循环）

1. **Thought 思考（Reason）**
把用户目标 + 历史对话 + 上一轮工具返回结果全部喂给 LLM。
模型思考：我现在信息够不够？是否需要调用工具？调用哪个工具、参数是什么？还是直接输出最终答案？
2. **Action 行动**
模型输出结构化工具调用指令（不是自然语言），**程序（框架）去执行工具**：向量检索（RAG）、联网搜索、代码执行、数据库查询等。

> 
> ⚠️ 注意：**工具不是大模型自己跑的，是外层代码执行**。

3. **Observe 观察**
拿到工具返回的结果（可以是文档片段、搜索内容、报错），打包成 Observation，追加进上下文 / 记忆。
4. **循环判定**
把新的完整上下文再次丢回 LLM，进入下一轮循环。**终止条件（满足任意就退出 loop）**

- LLM 判断信息足够，直接输出最终答案，不再调用工具 ✅
- 达到最大循环步数（防止无限死循环，工程必加）
- 报错、超时、人工干预终止

> 
> 流程图简写：
> 用户任务 →【Thought → Action → Observe】循环往复 → 输出答案

## 举个极简例子

用户：`查2026南昌9月平均气温，判断适不适合骑行`

1. Thought：我没有实时气候数据，需要调用搜索工具
2. Action：调用 search 工具，参数：南昌 9 月平均气温
3. Observe：工具返回：24~30℃，少雨
4. 回到 Thought：信息充足，不需要再调用工具，直接给出结论 → 退出 loop，输出答案

---

## 🔥 面试高频：Agent Loop 和普通 LLM 对话的区别

- 普通 LLM：单次推理，**没有外部工具反馈闭环**，信息全靠模型参数，容易幻觉
- Agent Loop：**多轮迭代闭环**，模型思考 → 动手查外部世界 → 拿到真实反馈再思考，用外部事实减少幻觉

## 相关同体系知识点（Agent 系列，面试一起问）

### 1. Plan-and-Execute（规划执行）

先一次性做完整大规划（把任务拆成子任务列表），再进入循环逐个执行子任务。

> 
> ReAct 是**边做边想**；Plan-and-Execute 是**先整体规划，再循环执行**。

### 2. Memory（记忆，和 Loop 强绑定）

- 短期记忆：本轮 loop 上下文窗口（每一轮的 Thought/Action/Observation 全部保存在 messages）
- 长期记忆：向量库，跨会话持久存储（RAG 就是长期记忆）

### 3. Tool Calling 工具调用

Loop 里面 Action 环节的核心能力，模型输出结构化 JSON，框架解析并执行函数。

### 4. Reflection（反思 / 自我校验）

Loop 变种：一轮做完之后，额外加一步反思，检查结果是否有错，有错继续循环修正。

### 5. Multi-Agent 多智能体

多个 Agent 各自跑自己的 Loop，互相传递消息、分工协作（比如一个写代码 Agent，一个测试 Agent）

### 6. Human-in-the-loop 人在回路

循环中可以暂停，交给人审核、输入指令，再继续跑 loop。

## 面试一句话背诵版

Agent Loop（ReAct）是**思考 - 行动 - 观察**的迭代闭环：LLM 思考决定下一步动作，外层程序执行工具拿到观测结果，结果回填上下文继续下一轮思考；循环直到信息充足输出答案或者达到最大步数。它让大模型可以分步解决复杂任务，利用外部工具获取真实信息，缓解幻觉。

2.迭代
(栈stack)
def inorder_iter(root):
    res = []
    stack = []
    cur = root   # cur 用来遍历节点，stack存路过的根节点
    while cur or stack:
        # ① 一直往左走，沿路节点全部压栈
        while cur:
            stack.append(cur)
            cur = cur.left
        # ② 左走到头了，弹出栈顶（取出根）
        cur = stack.pop()
        res.append(cur.val)
        # ③ 去访问这个根的右子树
        cur = cur.right
    return res

MQ

中间件,异步收发消息，结耦系统
producer-> broker（MQ服务器) ->consumer(接收消息）



三大核心功能
1.解耦
不需要直接http调用
2.异步
MQ 异步：下单主逻辑完成，发消息到 MQ 直接返回；短信、日志交给消费者后台慢慢处理。用户不用等。
3.削峰填谷(流量缓冲）
秒杀瞬间大量请求涌入。
请求不直接打到数据库，先全部丢进 MQ 队列；消费者按固定速度慢慢消费，保护数据库不会被瞬间压垮。

>

缺点：
会带来**消息可靠性问题**：消息丢失、重复消费、消息积压、顺序消息。



## 简单工作流程

1. Producer 发送消息 → MQ Broker
2. Broker 把消息存入队列
3. Consumer 监听队列，获取消息，处理业务
4. 处理完成后，消费者发送 ACK 确认，MQ 删除这条消息

- ACK：确认。消费者告诉 MQ：这条消息我处理完了，可以删掉。没 ACK，消息会重新投递。
- 消息重复：网络抖动，ACK 没传到 MQ → MQ 重发消息。业务需要做**幂等**。
- 消息积压：生产者发消息速度 > 消费者消费速度，队列消息越堆越多。



MQ 就是消息的 “中转站 + 缓冲池”，让系统之间异步通信，解耦、抗流量高峰。

1. **String 字符串**：最简单，key-value。可存数字、字符串；支持自增 `incr`。
场景：缓存、计数器、session。

场景：好友关系、去重。

场景：排行榜、热搜。





## 典型业务场景

1. **缓存（最常用）**：减轻 MySQL 压力，热点数据放 Redis，减少数据库查询。
2. **分布式锁**：多服务争抢资源。
3. **计数器**：访问量、点赞。
4. **排行榜**（ZSet）
5. **限流**
6. **简易消息队列（List）**，但生产级 MQ 一般用 RocketMQ/Kafka。






## 持久化（防止重启丢数据，两种方式）

1. **RDB 快照**：定时把内存全部数据拍一张快照存磁盘。
   - 优点：文件小，恢复速度快
   - 缺点：两次快照之间的数据可能丢失
2. **AOF 日志**：记录每一条写命令，重启重放命令恢复数据。
   - 默认：每秒刷盘，最多丢 1 秒数据
   - 优点：数据更安全；缺点：文件大，恢复慢

> 
> 生产一般**RDB+AOF 混合开启**。


## ✅ 缓存三大经典问题（高频）

1. **缓存穿透**：查询不存在的数据，直接打到 DB。解决：布隆过滤器、缓存空值。
2. **缓存击穿**：热点 key 过期，大量请求打到 DB。解决：互斥锁、永不过期。
3. **缓存雪崩**：大量 key 同时过期，DB 瞬间压力爆炸。解决：过期时间加随机值、集群、多级缓存。



## ✅ 内存淘汰策略

内存满了，自动删 key（常用 `allkeys-lru`，淘汰最近最少使用的 key）

## ✅ 缺点

- 受内存大小限制，不适合存海量冷数据
- 缓存带来一致性问题（缓存和数据库数据不一致）
：数据库内容更改，但redis内容没有同步更新；或者相反，两边数据不一致
## 不一致分两类

1. **短期不一致（正常，允许）**
数据库更新后，缓存还没来得及操作，这极短窗口内短暂不一致。
业务大多能接受，只要最后能同步回来。
2. **永久不一致（故障，不能接受）**
因为异常（崩溃、网络、并发竞争），缓存永远保留旧值，一直和数据库对不上。


解决方法：
1. **优先策略：更新 DB，删除缓存，而不是更新缓存**
2. **延时双删**：更新数据库 → 删除缓存 → 等几百 ms → 再删一次缓存。解决并发读带来的旧数据回写。
3. **给缓存加过期时间**：兜底方案。就算不一致，到期自动失效，下次查询重新加载 DB 数据。
4. **消息队列做异步更新**：DB 更新后发 MQ，消费者去删缓存。
5. **数据库 binlog 监听（Canal）**：监听 MySQL 变更日志，自动删除缓存，业务代码无侵入。





### MQ vs Redis 一句话区分

- **MQ**：异步消息，削峰、解耦，重点是消息流转。
- **Redis**：内存 KV 存储，主要做缓存、计数器、排行榜；List 可以做简易 MQ，但不适合高可靠消息场景。














































- 主从：数据备份 + 读写分离，**不会自动换主**
